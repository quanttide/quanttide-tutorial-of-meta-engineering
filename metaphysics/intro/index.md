# 形而上学入门

这个目录下的几篇正课走的是同一套动作：[用集合与逻辑描述系统的静态结构](./static-structure.md)、[用状态机描述系统的动态变化](./state-machine.md) 和 [把多个状态组合成一个系统](./composition.md)。进去之前先把这套动作本身说清楚。它走四步，次序不能颠倒。

## 业务需求

一句话：先问清「你到底在说什么」——把需求里的名词和规矩逐个钉住，说清它指什么、边界在哪、什么时候不成立。

例：需求里一句「只有管理员能删订单」，得先答三个问题：管理员是什么（角色集合里的一个值）、订单是什么（一个对象）、「能删」是谁的判断（一条规则，不是一个字段）。这三个问题答不清，后面写什么都白写。

## 哲学阐述

一句话：把摊开的东西放回本体论与范畴论的坐标上——有哪些东西存在，各自属于哪一类，这条规矩说的是一种状态、一种关系，还是一次动作。

例：「货发了钱没到」说的不是某个字段的取值，而是两个字段之间不许出现的组合，这类断言落在不变量上；「没收到钱不能发货」说的是动作的许可，落在前置条件上。归错位，后面写的规矩就拦不住人。

## 数学表达

一句话：把归好位的意图写成没有歧义的数学，让它可以被检查，而不是被理解。

静态的部分写成集合、关系、函数、逻辑式；动态的部分写成状态空间，加每个操作的前置、后置条件，再加一条永远不许被踩破的不变量。就像这样：

```text
State ::= paid    : Bool
          shipped : Bool
inv ≡ shipped ⇒ paid
```

这三行是上文那条业务规矩的另一种写法，读它不需要猜。

## 代码实现

一句话：把数学表达落到代码，让规矩由类型、函数和校验承担，而不是靠注释和默契。

集合落在代码里，是取值范围被限死的类型（枚举、联合类型）；关系落在对象引用或外键上；逻辑式落成一个校验函数。同一份描述换一种语言，差别只在两处：不满足条件时怎么报错（抛异常还是返回错误），以及状态放在哪（改对象本身还是返回新值）。

## 正课

- [用集合与逻辑描述系统的静态结构](./static-structure.md)：把数据模型、外键、业务规则写成集合与逻辑式。
- [用状态机描述系统的动态变化](./state-machine.md)：把状态变化写成状态空间、前置、后置条件与不变量。
- [把多个状态组合成一个系统](./composition.md)：状态维度变多时怎么拆开、怎么只做局部论证。
