# 形而上学入门

这个目录下的几篇正课走的是同一套动作：[用集合与逻辑描述系统的静态结构](./static-structure.md)、[用状态机描述系统的动态变化](./state-machine.md)、[证明实现没有削弱规格](./refinement.md)、[把并发摊成一组轨迹](./interleaving.md)、[把多个状态组合成一个系统](./composition.md) 和 [看清这套方法的数学形状](./categorical-view.md)。进去之前先把这套动作本身说清楚。它走四个阶段，次序不能颠倒。

## 为什么拿支付举例

因为这个场景不容许猜。

支付上每条规则都是钱的规则：金额不能错，钱不能重复扣，余额不能透支，退过款的不能再退。这里出错就是真钱出错，而测试只能撞到它撞得到的顺序——并发那一篇里那条「两个请求各自读到同一份余额」的交错，十次压测可能一次都撞不到。

要对付的正是「看起来对」的答案。让人写、让大模型写，都能给出一段像样的扣款代码；差别在于它有没有考虑并发、有没有漏掉某条状态规则，这两件事从代码长相上看不出来，它自己也不会说。形而上学这套分析方法的用处，就是把规则从直觉里搬到纸面上：有哪些东西存在，哪条规矩是状态约束、哪条是动作许可，哪些组合永远不许出现。搬完之后的结论可以被检查，不必被相信。

所以这几篇拿支付当靶子，不是因为读者熟悉它（那只是顺带），而是因为它有明确的正确答案、错一次就赔钱：方法有没有用，在这里当场看得见。

场景就这么大：账户、支付、订单三样东西，加几个状态取值。前面立下的状态、规则、不变量，后面几篇都在同一套上继续用。

## 需求

一句话：先问清「你到底在说什么」——把需求里的名词和规矩逐个钉住，说清它指什么、边界在哪、什么时候不成立。

例：需求里一句「退过款的支付单不能再退」，得先答三个问题：支付单是什么（一个对象），退款是什么（一次动作），「不能再退」是谁的判断（一条规则，不是一个字段）。这三个问题答不清，后面写什么都白写。

## 意图

一句话：把摊开的东西放回本体论与范畴论的坐标，写成没有歧义的数理逻辑，再交给机器验过。

先归位——有哪些东西存在，各自属于哪一类，这条规矩说的是一种状态、一种关系，还是一次动作。

例：「货发了钱没到」说的不是某个字段的取值，而是两个字段之间不许出现的组合，这类断言落在不变量上；「没收到钱不能发货」说的是动作的许可，落在前置条件上。归错位，后面写的规矩就拦不住人。

归好位再写成式子。静态的部分写成集合、关系、函数、逻辑式；动态的部分写成状态空间，加每个操作的前置、后置条件，再加一条永远不许被踩破的不变量。就像这样：

```text
State ::= paid    : Bool
          shipped : Bool
inv ≡ shipped ⇒ paid
```

这三行是上文那条业务规矩的另一种写法，读它不需要猜。写它不只为可以被检查，而是能交给机器验三件事：规矩之间矛盾吗，不变量证得出吗，前置条件够用吗。验不过，退回需求重谈。

## 规格

一句话：把验过的意图落成机器能读、但与编程语言无关的那份表达；规格只写一份，供多种语言共用。

例：支付的数据模型、状态表与接口契约写成一份中立的规格——字段是什么类型、状态有哪些取值、哪条规则查什么，都写死在规格里。Python、Rust、Go 各自的实现都对着它落，也由它裁定谁削弱了意图。规格本身在落到具体语言之前，就能先被 schema 与类型检查查一遍。

## 实现

一句话：把规格落到具体的编程语言，让规矩由类型、函数和校验承担，而不是靠注释和默契。

集合落在代码里，是取值范围被限死的类型（枚举、联合类型）；关系落在对象引用或外键上；逻辑式落成一个校验函数。同一份规格换一种语言，差别只在两处：不满足条件时怎么报错（抛异常还是返回错误），以及状态放在哪（改对象本身还是返回新值）。
