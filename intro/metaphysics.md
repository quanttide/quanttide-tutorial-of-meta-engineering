# 用形而上学识别问题，让设计从结构中长出来

有的需求一上手就知道不是表面看起来那么简单，却又说不清为什么。这时候直接跳去谈方案，谈出来的多半只是把需求里那句解决方案换个说法。这一篇给一条六步的路：先把问题本身的结构看清楚，设计再从结构里推出来。

拿一个具体的需求走完全程：我在电脑上用 pi 跑任务，出门之后想知道跑完没有，希望 pi 跑完就把消息经 hermes 发到微信。

## 一、悬置现象

第一步是把需求的包装剥掉，只看裸现象。

需求通常是用解决方案的语言说出来的——「pi 跑完通知我微信」就是一个已经被包装过的答案。剥掉包装，回到三个问题：发生了什么？谁在什么位置？什么东西断了？

做法是拿一张纸，把所有觉得「这里不只是表面那个意思」的点记下来，先不解释。对这个需求，记下来的困惑是三条。事件在 A 处、我在 B 处，这不是简单的网络传输，是存在论上的空间分离。pi 不知道「我」在等，缺的是意向性链条，不是数据管道。我要的不是数据而是「知道」，因为「通知」和「被召唤」是两件事。

检验标准：如果记下来的困惑点全都能用「加一个 API 调用」解决，说明还没挖到结构，继续问为什么——为什么需要这个 API，它解决的是哪一层的断裂。

## 二、范畴发明

第二步是为这个领域发明基本切分。不是从现成词汇里挑，是找到实在弯折的地方，在那里切。

做法分三小步：先列出所有「东西」——不是名词，是感知到的实体、事件、关系；再问这些东西在存在论上是不是同一类，不是就切开；最后为每个范畴写一句定义，定义说清「它处在什么层面」，不说「它做什么」。

这个需求切出来的范畴有五个。「任务跑完了」说的是事件，在某个时空中发生的状态变化，有内在的时间边界。「我在溜达」里的我是觉知者，具有注意力指向能力的实体。hermes 转发时的角色是信使，连接事件和觉知者的中介，职责是见证，不是搬运。微信是通道，觉知者已经打开的感知入口。最后，「我要被拉回来」是召唤，对觉知者注意力的一次拉动。

检验标准：范畴之间要互斥；一个东西能同时落进两个范畴，说明切得不够锐利。常见的错误是把功能描述当定义——「信使是传递消息的东西」说的是它做什么，「信使是见证者，把发生转成可知的发生」说的才是它在存在论上是什么。

## 三、关系建模

第三步是定义范畴之间的关系，搭出层级。

不是画流程图，是建立存在论上的依赖。画一张图，节点是范畴，箭头标注关系类型——产生（A 的发生导致 B 出现）、派生（B 以 A 为前提）、转化（A 经某种操作变成 B）、指向（注意力朝向）。最后分层：哪些是底层的（不依赖别的），哪些是派生的。

```text
事件      （本体层：不依赖任何主体）
  │ 产生
  ▼
信使      （见证层：把发生转成可知）
  │ 转化
  ▼
通道      （感知层：已有入口）
  │ 指向
  ▼
觉知者    （意向层：注意力被拉动）
```

检验标准：去掉某一层，结构还成立吗？去掉信使层，事件仍然发生，但没有人知道——这说明见证层不是装饰，是必要条件。去掉后会塌的那一层，就是核心层。

## 四、边界测试

第四步是拿反例和极端情况去戳框架，看哪里塌。

对每个范畴问三件事：它不存在会怎样（必要性）？它的职责被另一个范畴顶替会怎样（唯一性）？它的输入输出异常时框架还转得动吗（鲁棒性）？

这个框架戳出来的反例有四条。hermes 挂掉，事件沉没、无人知晓，说明见证层是必要条件，不是可选优化。我没看微信，召唤发出但没被接收，说明信使的承诺到「送达」为止，接收是觉知者的事。pi 直接发微信，短期可行、长期耦合，说明执行者和信使混在一起，扩展性会塌。事件是异常而非完成，召唤的紧迫性不同，说明事件类型影响召唤强度，得显式建模。

塌了不是失败，是信号：框架在说「这里还有一个没看到的关节」。回去改定义、加范畴，或者调层级。

## 五、元层反思

第五步是退一步看框架本身。

要问的是：这些范畴属于哪个更大的领域，能不能被一个更高层的框架容纳；除了当前这个问题，它还容得下哪些类似的问题；有没有什么在这个框架里说不出来——说不出来的是边界，不是缺陷，好的框架知道自己的沉默之处。

这套框架（事件 → 见证 → 通道 → 召唤）属于行动—感知存在论。它不止能装「pi 通知微信」，也能装多设备间的状态同步、任务依赖链里的条件触发、多主体协作里的事件广播。它装不了实时双向对话——那是另一个框架的事。这是边界。

## 六、设计从结构中长出来

到这里才进工程层。但设计已经被结构决定了：决策不再是「选 A 还是选 B」的权衡，而是「在这个位置上，什么符合结构」的推导。

五条结构原则各推出一条设计决定。范畴之间互斥，所以每个模块只承担一个范畴的职责。层间依赖单向，所以下层不知道上层，上层可以调用下层。见证层是必要条件，所以 hermes 不能是可选项，必须有。通道可替换，所以微信只是通道的一种实现，接口要抽象。召唤强度由事件类型决定，所以事件要带上类型或优先级。

这个需求长出来的设计是：pi 只做一件事，宣告事件；hermes 做两件事，见证（记录事件）和召唤（按事件类型选通道和强度）；微信是通道的一个适配器，可以换可以加；鉴权在信使层，不在通道层。

## 流程速查

1. 悬置现象——剥掉需求包装，记录困惑点。
2. 范畴发明——在关节处切割，给每个范畴存在论定位。
3. 关系建模——搭层级，标依赖和转化。
4. 边界测试——用反例戳框架，塌了就改。
5. 元层反思——确认框架的适用范围和边界。
6. 设计推导——从结构推出工程决策，不从便利凑方案。

这套六步，是把[形而上学入门](../metaphysics/intro/index.md)那四个阶段里「意图」到「实现」这一段走细。四个阶段各自在做什么，见那一篇。
